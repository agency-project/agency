# Shared container backend (`agsandbox_backends/container.py`)

> Covers `_ContainerBackendBase`, the shared implementation `_DockerBackend` ([docker.md](docker.md)) and `_PodmanBackend` ([podman.md](podman.md)) both subclass. See [base.md](base.md) for backend selection and [chroot.md](chroot.md) for the non-container alternative.

`_ContainerBackendBase` holds everything that doesn't differ between Docker and Podman — nearly everything, including the session-keyring-quota handling. What a leaf class overrides:

- **`_resolve_image(name)`** — identity for Docker (bare image names resolve fine); `_PodmanBackend` prefixes `localhost/` (Podman requires fully-qualified names when no unqualified-search registries are configured).
- **`_locate_layer_diff_dir(diff_id)` / `_host_to_container_id(uid, gid)`** — runtime-specific storage hooks for fast incremental checkpoint squashing (see "Fast incremental squashing" below); each backend reaches into its own on-disk layout.

Session-keyring-derived concurrency (`_acquire_runtime_slot()`/`_release_runtime_slot()`/`_is_quota_exhaustion_error()`/`_wait_for_quota_slot()`/`_quota_diagnostics()`) is **not** one of the things that differs: both Docker and rootless Podman (via `runc`) charge each running container's session keyring against the real host UID's kernel quota (`/proc/sys/kernel/keys/maxkeys`) identically — Podman's per-container user namespaces don't exempt it, since `runc` joins/creates the session keyring before the container process finishes transitioning into its remapped identity. (Confirmed empirically — `/proc/keys` gains a `_ses.*` entry owned by the real host UID across a plain `podman run`/`rm` cycle, same as docker — and upstream: containers/podman#13363, kubernetes-sigs/kind#3806.) Both `_DockerBackend` and `_PodmanBackend` therefore use the same concrete implementations on `_ContainerBackendBase`, described in [docker.md](docker.md)/[podman.md](podman.md).

Containers are created lazily: one starts only when a task actually calls `exec()` (any sandboxed tool touching the sandbox, not just ones flagged `run_in_subprocess=True` — that flag no longer gates whether the container gets stopped/checkpointed; see "Container lifecycle" below). Tasks that complete using only host-side tools (web fetch, `ask_human`, paper search, …) never create a container at all. After each sandbox tool call — success or failure — the container is stopped: committed to a lifecycle image and removed on success, discarded without committing on failure. The session keyring and GPU are freed at that point so other agents can use them while the LLM thinks. On the next tool call the container is recreated from the lifecycle image, restoring `/workspace` and all other state.

## Building the sandbox image

```bash
GPU_TYPE=cpu ./images/build.sh   # or nvidia/rocm; auto-detected if omitted
```

`build.sh` builds `agency-sandbox:latest` for **every container runtime installed on the host, podman first** — matching `agsandbox_backends.base._auto_detect_runtime()`'s auto-selection order (see [base.md](base.md)). An image built only for docker would leave podman's separate image store empty, so podman would try (and fail) to pull the image from a registry instead of finding it locally; building for both keeps whichever one auto-selection picks actually usable. Podman's build is tagged `localhost/agency-sandbox:latest` (the `localhost/` prefix it requires to resolve an unqualified name to its own local store instead of a registry, matching `_PodmanBackend._resolve_image()` — see [podman.md](podman.md)); docker's is tagged bare. Each build gets its own smoke test (`import torch`) run against the runtime that built it.

If `HF_TOKEN` is set, it's passed as a `--secret` for gated model downloads during the build. This is written to a private temp file and passed as `--secret id=hf_token,src=<file>` for both runtimes — docker buildx's `--secret id=...,env=VAR` shorthand is **not** portable to podman's buildah, which rejects it ("incorrect secret flag format: should be `--secret id=foo,src=bar`"); the file-based form is the one both accept.

The `images/Dockerfile` installs `ripgrep` on top of `python:3.12-slim`. `Dockerfile.nvidia`/`Dockerfile.rocm` are used instead when `GPU_TYPE` is `nvidia`/`rocm`.

## Container lifecycle

The container exists only during active tool execution. Between tool calls the container is removed, releasing the Linux session keyring (both runtimes) and any held GPU so concurrent agents can use those resources.

| Event | What happens |
|---|---|
| `agSandbox.__init__` | No container created — cheap object; `_lifecycle_image=None` |
| Any tool call that touches the sandbox | `_ensure_started()` runs lazily: ground truth is always `_container_running()` (a real `docker/podman inspect`), never a per-process flag — see "Cross-process safety" below. If already running, reuse it; otherwise `docker rm -f`/`podman rm -f` any leftover zombie, then `run` from `_lifecycle_image` (or `base_image` on first use) |
| After a tool call, unless background work is still pending | `agtool.py`'s `dispatch_tools()` calls `sandbox.stop(commit=...)` after every tool call — success or failure — regardless of `run_in_subprocess`, **unless** `sandbox._has_pending_background_work()` is true, in which case `stop()` is skipped entirely for that call rather than killing a job the agent just backgrounded. A later tool call that finds nothing pending is what actually checkpoints/tears down. |
| `sandbox.stop(commit=True)` (successful tool call) | `commit → agency/lifecycle-<name>` (retried up to 3×, flattened via `export`/`import` instead once the chain's actual depth reaches `checkpoint_squash_max_depth` — see "Layer-depth squashing" below); `rm -f` (retried up to 3×); `_lifecycle_image` updated; GPU released once the container is confirmed gone |
| `sandbox.stop(commit=False)` (failed tool call) | `rm -f` without commit (retried up to 3×); dirty state discarded; next start restores from previous `_lifecycle_image` |
| Any non-running container detected at startup | Force-removed with `rm -f` before `run` — covers "Exited", "Created" (partial run), and "Dead" states |
| `sandbox.destroy()` | `rm -f` (no-op if already removed); GPU released once confirmed gone; `rmi agency/lifecycle-<name>` |
| `atexit` | All live containers removed (guard against hard-killed processes) |

**Layer-depth squashing**: `docker/podman commit` always creates one new layer on top of whatever the container was started from, and `_ensure_started()` always restarts the next container FROM the last checkpoint image — so a long-running sandbox's layer chain grows by exactly one every `stop(commit=True)` cycle, with nothing bounding it, until it eventually crosses the container runtime's hard layer-depth cap (~125 layers observed empirically on this host's docker/moby, surfaced as `Error response from daemon: max depth exceeded`). To bound this, a squash — `docker export <container> | docker import - <tag>` (via `_squash_commit()`), serializing the container's *full* filesystem into a brand-new image with no parent chain at all and resetting depth back to 1 — is triggered in `stop()` by **either** of:

- **`force_squash=True`** (used at skill exit — see below).
- **`checkpoint_squash_max_depth`** (default `100`): the chain's *actual* current depth (`len(_image_diff_ids(tag))`, a cheap `docker/podman inspect` — not proportional to image size) reaching this, checked every commit cycle.

There is no fixed commit-count interval: an earlier version squashed every Nth commit (tracked by a plain counter), but a count alone can't account for how many layers the *base* image itself already consumes — a real base image was found to already have 80 layers on its own, so `base_depth + interval` (80 + 60 = 140) exceeded the runtime's real cap (~125) *before the interval ever fired* — exactly what caused a real `max depth exceeded` failure on an ordinary plain commit, with squashing never having triggered at all yet for that sandbox. Checking the chain's actual depth directly removes that whole class of failure: it's correct regardless of how deep the base image is, needs no tuning per base image, and is exactly as cheap as maintaining a counter (one inspect call, same cost independent of image size). A failure to inspect (unparseable output, runtime unreachable) is caught and logged; that cycle just skips the squash check and tries again next cycle. This is safe to do because `_ensure_started()`'s restart `run` command always passes an explicit `tail -f /dev/null` — it never relies on anything `docker commit` bakes into the image (env, labels, `CMD`/`ENTRYPOINT`) that `export`/`import` would otherwise drop. `squash_timeout_s` (default `600`) is longer than `commit_timeout_s` since export/import serializes the whole filesystem rather than an incremental diff.

**Squashing and dangling images — what actually gets reclaimed, and when**: a container runtime refuses to delete an image while any other image depends on it as a parent (`docker rmi` fails with "has dependent child images"). A plain commit's result IS a child of whatever it replaces, so **two consecutive plain-commit cycles can never free the first one's image** — this is an unavoidable property of layered images, not a bug, and dangling images genuinely accumulate between squash points. Because of this, `stop()` doesn't even attempt the old-image lookup/delete on a plain-commit cycle — it's guaranteed to fail, so trying would only cost an extra `inspect`/`ps`/`rmi` round-trip per checkpoint and print a permanent, misleading `WARNING` on the vast majority of cycles (this was the original, pre-fix behavior: every ordinary checkpoint logged a "could not check/delete old image ... has dependent child images" warning that meant nothing more than "as expected"). The lookup only happens at all when this cycle's commit was determined to be a squash (`force_squash` or the depth check above). A squash's image is parentless — nothing in the runtime depends on the prior chain anymore, so that lookup's `docker rmi` finally succeeds, and removing an image cascades to free every one of its now-unreferenced ancestor layers at once. In other words: squashing doesn't just bound layer depth, it's also the only point at which the accumulated interim disk cost actually gets reclaimed — in one lump sum, at the next squash, not incrementally. Confirmed live: `tests/agsandbox_backends/test_docker.py`'s `test_real_plain_commit_cycle_cannot_delete_its_parent` and `test_real_squash_cycle_reclaims_the_entire_prior_chain`.

**Fast incremental squashing**: the export/import squash above is always correct but always pays for the *entire* merged filesystem — fine at moderate image sizes, but proportional to total image size regardless of how little actually changed, so a large base image (tens of GB) makes every squash a multi-tens-of-seconds stall. `_accumulator_squash_commit()` is a faster alternative attempted first, falling back to `_squash_commit()` (export/import) on any failure — never raised as a hard error, since a slower-than-ideal squash is still a correct one.

The key insight: every `docker/podman commit` already does the expensive work of isolating *just* the container's changes (its overlay2 upper/copy-on-write "diff" directory) — `docker commit`'s own cost is small and independent of base image size for exactly this reason. What's missing is a cheap way to *read* that same isolated diff back out, and a cheap way to build a new image from `base + accumulated diffs` without re-serializing the base. Both `docker diff` and `docker save` were considered and rejected for this: `docker diff`'s cost is proportional to the image's total file count (confirmed empirically — two consecutive calls with zero container changes between them both cost ~9s against the real base image), and `docker save` of a full layer chain is proportional to total image size, same as export/import. Neither is safe to call every checkpoint cycle. The mechanism actually used instead:

- **Per-cycle, best-effort folding** (`_fold_commit_into_accumulator()`, called right after every successful plain commit in `stop()`): locates the new layer's raw overlay2 diff directory directly on disk via `_locate_layer_diff_dir()` (see below), converts it to a portable layer tar (`_layer_squash.overlay_diff_to_tar()` — this is also where kernel-style overlayfs whiteouts, a `0,0` char-device at the deleted path, get translated to the portable `.wh.`/`.wh..wh..opq` tar convention), and merges it into a single running accumulator tar (`_layer_squash.merge_layer_tars()`) representing the flattened union of every cycle's diff since the last squash. This reads only the small set of files the container actually touched — never the base image — so it's cheap regardless of base size. Any failure at any step (diff dir not found, merge error) invalidates the accumulator rather than raising; the next squash attempt just falls back to export/import.
- **At squash time** (`_accumulator_squash_commit()`): validates the accumulator's layer count matches the number of new layers actually added since the *reference chain* (and that the reference chain's own layer digests are still a prefix of the current chain — catching e.g. a fork that reset the lineage), then builds a `docker`/`podman load`-compatible archive (`_layer_squash.build_save_archive()`) that references the reference chain's existing layer blobs by digest only — never reading or copying their real content — and adds just one new blob: the accumulated diff tar. Both runtimes resolve those digests from their local store; Podman additionally requires each referenced `blobs/sha256/<hex>` path to exist as an archive member, so the builder writes zero-byte placeholders for those digests (Docker tolerates the same). Confirmed empirically, including against the real base image — this is what makes the whole approach avoid ever touching the base image's bytes. On success, this produces an image with exactly one more layer than the reference chain had (its own top layer identity is preserved as history, plus one new flattened layer) instead of one accumulated layer per cycle.

**Re-baselining after a fallback**: the "reference chain" above is `self._squash_base_diff_ids` if this backend has squashed successfully at least once already (fast or fallback), else `self._base_image`'s own digests. Both `_accumulator_squash_commit()` and `_squash_commit()` set it to the chain they just produced, on success. Without this, a single `_squash_commit()` fallback would be permanent for the rest of a sandbox's life: export/import produces a parentless image, disconnected from `self._base_image`'s lineage forever, so the base's digests can never be a prefix of the chain again — every subsequent squash would fall back too, no matter how small its own diff was. Re-baselining against whatever the *last* squash actually produced (referenced by digest, never by re-reading the mutable lifecycle tag, which gets overwritten by the very next commit) means only the squash that actually fell back pays the export/import cost; the next one gets a fresh reference chain and a fresh accumulator, recovering fast-path eligibility. This matters in practice: a real long-running sandbox with unusually large per-commit diffs (e.g. an agent whose job is installing large ML packages) hit a one-time lookup failure, fell back once, and — before this re-baselining existed — was then permanently stuck re-paying a multi-tens-of-GB export/import on every subsequent squash for the rest of its life, even though the underlying diff-lookup mechanism itself was working fine. Purely in-memory (`self._squash_base_diff_ids` is a plain instance attribute): a fresh backend object (a new process, or a fork — see "Fork safety" below) starts back at `None`, falling back to `self._base_image` for its own first squash, same as before this existed.

**Runtime-specific storage hooks**: `_locate_layer_diff_dir()` and `_host_to_container_id()` (below) are hooks on `_ContainerBackendBase` following the same override pattern as `_resolve_image()` — a safe generic default (`_locate_layer_diff_dir` returns `None` unconditionally; `_host_to_container_id` is identity) that `_fold_commit_into_accumulator()` treats as "fast path unavailable, squash will fall back to export/import" rather than an error. Both concrete backends override them against their own storage layouts (confirmed empirically during development, not from a single published "how to find a layer's diff dir" doc):

- **`_locate_layer_diff_dir(diff_id, *, diff_ids=None)`**:
  - `_DockerBackend`: dispatches on `docker info`'s `Driver`:
    - `overlay2` (classic moby graphdriver): `<DockerRootDir>/image/overlay2/layerdb/sha256/<entry>/diff` → `cache-id` → `<DockerRootDir>/overlay2/<cache-id>/diff/`.
    - `overlayfs` (containerd snapshotter, `io.containerd.snapshotter.v1`): computes the layer's ChainID from the full `diff_ids` RootFS.Layers prefix (ChainID is not the tip DiffID alone), then resolves it via `ctr -n moby snapshots view` + `mounts` to `/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots/<id>/fs/`. Bare `ctr` is tried first; passwordless `sudo -n ctr` is a fallback for rootful installs whose containerd socket is root-only. When sudo was needed, the located `snapshots/<id>/` directory is also `chmod -R a+rX`'d (rootful containerd creates those as `0700`) so the subsequent tar conversion can read it — scoped to that one snapshot, not the whole containerd tree.
    - any other driver: `None`.
  - `_PodmanBackend`: correlates via Podman's `containers/storage` overlay layout (`<graphRoot>/overlay-layers/layers.json` entry whose `diff-digest` matches → storage layer `id` → `<graphRoot>/overlay/<id>/diff/`), reached via `podman info`'s `store.graphRoot`/`store.graphDriverName` (returns `None` for any non-`overlay` driver). The storage layer `id` is not always equal to the digest hex (especially for `podman commit`-produced layers), so the layers.json indirection is required. Ignores `diff_ids` (DiffID alone is enough).
- **`_host_to_container_id(uid, gid)`**: translates HOST-side ownership into CONTAINER-visible ownership. Needed specifically because **rootless** Docker/Podman remap ownership, so a raw `os.lstat()`/tar read of the overlay diff directory reports HOST-remapped ownership rather than what the container itself sees (confirmed empirically: a root-owned file inside the container showed up owned by the invoking host user via the raw overlay path) — without this translation, `docker`/`podman load`'ing the accumulated diff back in fails outright (`failed to Lchown ... invalid argument`) since the wrapper archive's entries must carry `uid=0/gid=0` but the merged layer's *own* file ownership must still be translated correctly.
  - `_DockerBackend`: detects rootless mode via `docker info`'s documented `SecurityOptions` field (`name=rootless`), finds the daemon's own PID (a process literally named `dockerd`, owned by the same host user — true by construction for rootless Docker), and reverse-maps host uids/gids through that PID's `/proc/<pid>/uid_map`/`gid_map`.
  - `_PodmanBackend`: detects rootless mode via `podman info`'s documented `host.security.rootless` boolean, and reverse-maps through `host.idMappings` (`uidmap`/`gidmap`) directly — Podman exposes the maps on `info` itself, so no PID discovery is needed.
  - Identity (no translation) for non-rootless Docker/Podman, where the overlay diff directory's on-disk ownership already matches what the container sees.
- **Fork safety**: `_accumulated_layer_count` and `_squash_base_diff_ids` are plain instance attributes not copied by `fork()` — a fresh fork's accumulator starts empty and its reference chain starts at `None`, and the layer-count/prefix mismatch check above naturally (and safely) detects this, falling back to export/import rather than risking an incomplete squash. Unlike a mid-life fallback on an already-running backend, this isn't something re-baselining fixes for the fork itself: the fork's *own* first squash still falls back once (same as always), it just then re-baselines from there for any squashes after that, within the fork's own lifetime.

Covered by `tests/agsandbox_backends/test_docker.py`'s `TestLocateLayerDiffDir`, `TestHostToContainerId`, `TestCheckpointAccumulator` (including a real end-to-end run against the actual multi-tens-of-GB base image), `tests/agsandbox_backends/test_podman.py`'s matching Podman classes, and `tests/agsandbox_backends/test_layer_squash.py`.

**Failure revert**: when a tool errors, `stop(commit=False)` discards the container with its partial state. The next tool call recreates from the last successful `_lifecycle_image`, so the agent's workspace is automatically rolled back to the last known-good state. The agent receives `workspace_reverted` in the error response — but only when `stop()` actually ran; if it was deferred because background work was still pending, no such note is added, since nothing was actually reverted yet.

**Container naming**: each container is named `sandbox-{RUN_ID}-{agname}`, where `_RUN_ID` (`agsandbox_backends.container._RUN_ID`) is a per-process UUID prefix. This prevents cross-run name collisions when an agent crashes without cleanup and is restarted with the same `agname`. The lifecycle image name is produced by `_lifecycle_tag()`, which lowercases the image name — both runtimes require all repository names to be lowercase.

**`stop()`/`destroy()` reliability**: `rm -f` is retried up to 3 times (each attempt through `_run()`, which holds `_get_docker_semaphore()`'s semaphore — caps all concurrent daemon calls, both runtimes, at 16). Unlike an earlier version of this backend, a persistent failure is **not** silently swallowed:

- `stop()` still attempts every remaining step regardless (the commit-retry block, if any; the runtime-slot/GPU release checks, both gated on the container being confirmed actually gone) but then **raises** the underlying exception at the end — a commit failure and an `rm` failure can both have occurred; the `rm` failure is raised in preference, since an unconfirmed removal is more severe (real resources may still be held) than a missed checkpoint.
- The old-image cleanup's `docker ps --filter ancestor=<old_image_id>` "is anything still using this?" check runs **after** `_rm_container`, not before, and is skipped entirely if removal failed. Checking before removal was a real bug (fixed alongside the squashing work above): this container was itself `run` FROM `old_image_id` — that's what restart-from-checkpoint means — so the ancestor filter always matched *this same, about-to-be-removed container* and reported a false "still in use," silently no-oping the cleanup every single cycle. Checking after removal means only a genuine fork still running from that image can block it now.
- `destroy()` follows the same cleanup-then-raise shape: it still runs the GPU-release check and the checkpoint image cleanup even if `rm -f` failed, then raises at the end. This matters because `destroy()` is called from `atexit`/`agSandbox.__del__` — a raise there is caught and logged by the atexit wrapper, not fatal, but skipping the rest of cleanup on the first failure (the old behavior) meant a failed `rm` could also leave a dangling checkpoint image behind forever.
- The non-critical cleanup steps — the old-image inspect/delete after a re-commit, and the checkpoint image deletion in `destroy()` — remain best-effort: they print a `WARNING` and continue rather than raising, since a stray dangling image costs disk space, not correctness.
- `destroy()` used to also list **every** image on the daemon (`docker/podman images`) to find and delete `agency/pretool-<name>-*` snapshots. That mechanism dates from an older per-tool-call checkpoint/revert design (removed when the sandbox lifecycle was refactored to the current commit-only-on-success model — see "Failure revert" above): no code path creates `pretool-*` images anymore, so the scan matched nothing and only added a full, unscoped image-list round-trip to every single `destroy()` call. Removed entirely, along with `chroot.py`'s equivalent (`_CHROOT_SNAPSHOTS_DIR` prefix scan).

## Cross-process safety

There is no `self._started` cache anywhere on this backend (or any backend, as of the same redesign) — ground truth for every decision (`_ensure_started()`'s reuse-vs-recreate branch, `stop()`'s and `destroy()`'s early-return/no-op checks) is always `_container_running()`, a real `docker/podman inspect` call, never an in-memory flag. Tool calls with `run_in_subprocess=True` (the default) each get a *fresh* cloudpickled copy of the backend dispatched to a `ProcessPoolExecutor` worker, so a per-process flag would only ever reflect what the object looked like at the *original* process's last pickle — never what a different worker already did to the real container. Every call pays the cost of a real inspect rather than a cached read; the alternative (trusting a flag that could be stale in exactly the case that matters most) was the source of a real bug: a container started by a worker process being invisible to the orchestrating process's own stale flag.

## Orphaned container reaping

`atexit` handlers (the row above) never run if the execution process is killed with `SIGKILL` — that signal can't be caught by any process, so the interpreter never regains control to remove its live containers. A framework-level `SIGTERM` handler (`agutil.sigterm_as_exit()`, used by `agwebui.run()`/`graphui.run()` — see [agwebui.md](../agwebui.md#shutdown-and-signal-handling)) closes that gap for plain `kill`, but SIGKILL still leaves containers behind. `_RUN_ID` being a per-process random UUID (see "Container naming" above) means the *next* run can't just guess an old container's name to reclaim it — it's deliberately randomized to prevent name collisions across runs, not to enable this.

Instead, every container is labelled at `run` time with the PID of the process that owns it:

```
--label agency.owner_pid=<pid>
```

**`self._owner_pid` is captured once, in `_ContainerBackendBase.__init__`**, as `os.getpid()` at construction time — not read live inside `_ensure_started()`. This matters because a tool call with the default `run_in_subprocess=True` dispatches through a `ProcessPoolExecutor` (`agtool.py`), so `_ensure_started()` (and the `docker run` call it makes) can execute inside a **worker** process with its own transient PID, distinct from the main process that actually owns the sandbox's lifecycle. Labelling with a live `os.getpid()` call there would tag containers with a worker PID that exits as soon as the tool call returns, making every container look orphaned to the next reap almost immediately. Capturing the PID once at construction — always in the main process — avoids that.

**At startup**, `_ContainerBackendBase.__init__` calls `reap_orphaned_containers()` (also exported from `agsandbox_backends`) before anything else. It:

1. Lists all containers (any runtime) carrying the `agency.owner_pid` label, via `docker ps -a --filter label=agency.owner_pid --format ...`.
2. For each, checks whether the labelled PID is (a) this process's own PID (skip — it's a container this same run is about to reuse) or (b) still alive on the host via `_pid_alive()` (`os.kill(pid, 0)`; skip if alive).
3. Anything left — labelled with a PID that's neither this process nor alive — is a dead run's container. It's force-removed (`rm -f`) along with its lifecycle image tag (`rmi -f agency/lifecycle-<name>`), and a message is printed noting the reap and the dead owner PID.
4. Separately, `_reap_orphaned_lifecycle_images()` scans `agency/lifecycle-*` **images** directly (`docker images --filter label=agency.owner_pid`), independent of whether their container still exists — the container-based sweep above only helps when the owning container is still around to check; once it's already gone (e.g. removed by anything other than this reaper, including external tooling that never invokes Python at all), its image would otherwise be unreapable forever, since nothing else ever revisits it. Same dead-PID check as above, plus one extra safety guard: before deleting, it also confirms no container (running or not) currently exists with that image as its ancestor (`docker ps -a --filter ancestor=<tag>`) — needed because a lifecycle tag can carry a **stale, foreign** label. The clearest case: `agent.save()` embeds a sandbox's image inside a portable `.ckpt` file (`docker save`, which — unlike `export`/`import` — *does* preserve labels), so without further handling the embedded image would still carry whatever PID committed it, from a process that might not even be on the same host. `agent.load()`'s `relabel_owner_pid()` call (`_ContainerBackendBase.relabel_owner_pid()`, via a throwaway never-started `docker create` + `commit --change`) fixes this in both directions: `save()` scrubs the label to empty before embedding, and `load()` re-stamps it with the actually-current restoring process's own PID right after import — but until that restamp runs, or for any restored image this fix predates, the label could reflect a long-dead (or coincidentally-reused, unrelated) PID while a genuinely-live container is running from that same tag.

Runs only once per process (`_reap_done` flag guarded by a lock) — every subsequent `agSandbox`/backend construction in the same process is a no-op. Any exception during the reap (no container runtime available, daemon unreachable, etc.) is caught and logged as a `WARNING`; it never blocks startup.

This is best-effort cleanup, not a substitute for `sigterm_as_exit()` — it only reclaims resources at the *next* run's startup, and only if something runs `_ContainerBackendBase.__init__` again on the same host afterward.

**Why `docker commit` needs no extra work but `_squash_commit()`'s export/import fallback does**: `docker commit` propagates a container's labels onto its image automatically, so every ordinarily-committed lifecycle image already carries `agency.owner_pid` for free. `export`/`import` doesn't preserve container config at all (confirmed empirically), so `_squash_commit()` explicitly re-applies the label via `docker import --change 'LABEL agency.owner_pid=<pid>'` — without this, any image that ever went through a fallback squash would be permanently invisible to step 4 above, exactly the situation that let real abandoned lifecycle images accumulate on a production host despite this reaper already existing (their container was long gone, and their image predated this fix, so neither half of the reaper could see them).

## GPU device access

GPU passthrough flags are passed to `run` when a GPU is detected on the host (`agsandbox_backends.container._gpu_flags(runtime)`, cached per runtime via `agresources.detect_gpus()`). On CPU-only hosts no flag is passed. NVIDIA differs by runtime — Docker uses `--gpus all` (nvidia-container-toolkit's Docker-specific CLI hook), while Podman needs `--device nvidia.com/gpu=all` (CDI) instead: Podman silently accepts `--gpus all` without erroring, but never mounts the driver/devices, so a container started that way has no GPU access at all despite `podman run` succeeding. AMD/ROCm uses `--device /dev/kfd --device /dev/dri` for both runtimes identically.

Even with those flags, GPUs are **not accessible by default** — every `exec()` call unconditionally exports `CUDA_VISIBLE_DEVICES="NoDevFiles"` when no virtual reservation is active, making all GPUs invisible to CUDA (readonly-exported, so a command can't hijack a different GPU by reassigning the variable inline). Calling `reserve_gpu` sets only a virtual flag; no physical GPU is taken yet. When `exec()` runs a bash command and the virtual flag is set, a physical GPU is claimed from the pool at that moment (blocking until one is free) and `CUDA_VISIBLE_DEVICES=<id>` (and `HIP_VISIBLE_DEVICES=<id>` for ROCm) is injected.

**GPU release is tied to the sandbox's lifetime, not to individual exec() calls.** There is no `_gpu_is_clear()`/polling mechanism at all (removed entirely, on every backend) — `agResourcePool.release_gpu()` releases the semaphore immediately, unconditionally, with no wait. Safety comes purely from call ordering: `stop()`/`destroy()` always remove the container (a real, structurally-guaranteed kill of everything inside it) *before* releasing the GPU, so by the time release happens the container — and anything that might have been using the GPU — is already confirmed gone. There is also no agent-facing `gpu_release` tool anymore: once `reserve_gpu` triggers a real acquisition, the GPU is held until `stop()`/`destroy()` tears the sandbox down, not released back mid-skill on request.

## Forking

```
parent.sandbox._checkpoint_image ──tag_image──▶ agency/lifecycle-<fork-agname>
                                            │
                                     (consumed by fork's first _task())
```

Forking copies the parent's checkpoint image tag to a new tag for the fork via `type(parent.sandbox._backend).tag_image(...)` — dispatched to whichever backend class actually produced the checkpoint (`docker tag`/`podman tag` here, a directory copy for chroot — see [chroot.md](chroot.md)), not a bare docker-only call, since a chroot snapshot directory and a docker/podman image tag are unrelated formats. No container is created at fork time — that happens lazily when the fork's first `_task()` runs, restoring from the copied tag.

Because forks wait for `src.ctx.resolve_prev_dependencies()` before construction, the parent's task is always complete before the fork is built, so the checkpoint image is already the committed post-task state.

## Static image-level helpers

`tag_image`/`delete_image`/`export_image`/`import_image` are `@staticmethod`s on `_ContainerBackendBase` that all call `get_container_runtime()` internally to pick the live runtime — they're runtime-agnostic by construction, so both `_DockerBackend` and `_PodmanBackend` share the exact same implementation rather than each needing their own.
